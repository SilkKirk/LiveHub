## 第四十一轮迭代：抖音搜索打到一个不存在的端点

### 缺陷是什么

搜索页切到「抖音」，输入房间号 `1002683794` 回车，界面直接打印：

```
搜索失败
HTTP 404 for https://live.douyin.com/webcast/search/partition/room/?device_platform=webapp&aid=6383&...&a_bogus=…
```

不只是搜不到，还把整条带签名的 URL 甩在页面上。用户对照的参考项目能出结果。

### 为什么会这样

**一、那个路径不存在。** 2026-11-04 实测三个域名：`live.douyin.com`、`www.douyin.com` 都回
`404 Page not found`，`webcast.amemv.com` 回 `404 Not Found`。参数是照着 App 端搜索接口
（`device_platform=webapp`、`search_channel=aweme_live`…）抄的，host 却用的是
`live.douyin.com`，路径本身从来没有存在过——两个来源拼在一起，谁也没验证过。

**二、真实存在的关键词搜索要登录。** `www.douyin.com/aweme/v1/web/live/search/` 回
`status_code = 2483` / `「请先登录，再继续搜索吧」`（带 ttwid cookie 也一样）。本应用没有
抖音账号，这条路走不通。

**三、第二十五轮的记录是错的。** 那一轮写"参考项目根本没有抖音搜索"，依据是全仓库 grep
`webcast/search`。实际参考项目的搜索在 `AndroidDtvRepository.searchAnchors` 里：
`Platform.Douyin -> runCatching { douyinWebApi.fetchRoomEnter(trimmed) … }`——它搜的就是
**房间号**，用 `room/web/enter` 解析出一张卡，`roomId` 保持用户输入的那串数字，`isLive` 由
hls/flv map 是否为空判断；搜索框占位文案是「输入抖音房间号（webRid）...」。当时只 grep 了
`douyinSearch` 这类名字，漏了内联分支。

### 怎么修的

按参考项目的形状实现，而不是继续猜关键词接口：

1. `DouyinApi.search(keyword, page)`：纯数字 → `enterRoom(id)` 拿一张卡（`roomId` 用输入值，
   因为 `roomDetail` / `playback` / 关注列表后面都把它当 `web_rid` 传回去）；非数字 →
   `PlatformAuthRequiredException`，说明"网页版搜索要登录、只支持房间号"，不再发请求；
   第二页 → 空（一个 id 只有一张卡）。
2. `roomInfo` 拆出 `enterRoom(...): DouyinRoomInfo?`：搜索路径上"没有这个房间"是空结果，
   房间页仍然抛原来的 `抖音直播间信息获取失败`，行为不变。
3. 删掉 `URL_SEARCH` 与只被它调用的 `parseRoomCard`。
4. 搜索框文案按平台走：抖音显示「输入抖音房间号」，不再写「搜索 抖音 主播 / 直播间」。
5. README「已知限制」里那条"参考项目没有实现搜索"按源码更正。

- **没有真机回归**：本机只验证了端点与解析，CI 只验证分支与解析；真正"输入号码出卡"要用户在

### 下一轮（本轮顺手查实的一条，未修）

`PlaybackSource.room`，而 `DouyinAdapter.playback` 的 `room = resolved.info.toStreamer()`，
`DouyinRoomInfo.roomId` 取的是 `room.id_str`（内部 id，如 `7703900142109592362`），不是
`web_rid`。于是从播放页点关注，写进关注列表的是内部 id；之后
`FollowRefreshWorker` 用 `liveStatus(roomId=内部 id)` → `enter?web_rid=<内部 id>` 实测回
`status_code 4001038`、0 个房间——这张卡永远"未开播"，点进去也打不开。
建议改法：适配器返回的 `Streamer.roomId` 一律保持调用方传入的 `web_rid`
（`info.copy(roomId = roomId).toStreamer()`，`roomDetail` 与 `playback` 两处），
`DouyinRoomInfo.roomId` 留给弹幕/播放内部用。本轮只修搜索，未动它。

## 第四十二轮迭代：播放页把抖音房间换成内部 id——从播放页关注的房间打不开

### 缺陷是什么

从搜索或分区点进一个抖音房间，在播放页点关注，关注列表里会出现这张卡，但这张卡：

- 永远显示"未开播"（后台刷新拿不到状态）；
- 点进去打不开，报"抖音直播间信息获取失败"。

第四十一轮末尾查实后记进了待办，本轮修。

### 为什么会这样

`MainViewModel.openRoom` 在播放源解析成功后，会把 `state.room` 换成 `PlaybackSource.room`。
抖音的 `PlaybackSource.room` 来自 `DouyinRoomInfo.toStreamer()`，而 `DouyinRoomInfo.roomId`
取的是 `enter` 响应里的 `id_str`（内部 id，如 `7703900142109592362`），**不是** `web_rid`
（房间链接里那串数字，`1002683794`）。播放页的关注按钮写的正是 `state.room`，于是关注记录里
落的是内部 id；之后：

- `FollowRefreshWorker` → `liveStatus(roomId = 内部 id)` → `enter?web_rid=<内部 id>`；
- 点卡片 → `playback(内部 id)` → 同一个 `enter`。

实测（2026-11-04，本机 python 直连）：`enter?web_rid=7703900142109592362` 回
`status_code = 4001038`、0 个房间；`enter?web_rid=1002683794` 回 200、536 241 字节、标题
「我的红眼看了不烧心！！」。所以这条记录既刷新不了状态，也打不开。

### 两个 id 的分工（本轮写清）

- **`web_rid`**：房间在应用里的身份。URL、搜索、分区列表、关注列表、`roomDetail` /
  `playback` 的参数，全是它。
- **`id_str`**：弹幕握手要的数字房间号。只在 `DouyinRoomInfo` 内部用——`danmaku` 先尝试从
  房间页 HTML 解析 `room.id_str`，解析不到才回落到 `roomInfo().roomId`。

把内部 id 默认当成"房间号"传出去，就是这一轮的 bug。

### 怎么修的

- `DouyinRoomInfo.toStreamer(roomId: String)`：参数**必填**（去掉默认值，让同一个坑不可能
  再犯一次），文档写明两个 id 的分工。
- `DouyinAdapter.roomDetail` / `playback` 传调用方用的 `roomId`；`DouyinApi.search` 传用户输入。
- 顺带核了另外三个平台：斗鱼、虎牙、B 站的 `roomDetail` / `playback` 本来就把调用方的 id
  传下去（虎牙 `parseRoomHtml(roomId, …)` 也是），**只有抖音漏了**。

接口（`webcast/room/web/enter` 之外有没有只回状态的端点需要实测）、限制并发并缓存结果、
或把刷新做成可见的后台批处理。这属于性能改造，需要单独一轮并先量基线。

## 第四十三轮迭代：抖音扫码登录 + 登录后按昵称搜索

### 需求

用户要求三件事：抖音扫码登录、抖音按名字搜索、抖音/B 站登录信息同步。本轮做前两件——顺序不是
选的，是接口决定的：**关键词搜索必须有登录态**。

### 先确认的事实（本机实测，2026-11-04）

- `www.douyin.com/aweme/v1/web/live/search/` 对匿名请求回
  `status_code = 2483` / `「请先登录，再继续搜索吧」`。试过三种请求：只有几个参数、照
  `dart_simple_live` 的完整参数表、再加协商出来的 `ttwid`，**三次都是 2483**。所以"按名字搜索"
  不能在没有登录的情况下做出来。
- 抖音没有可用的"取二维码"接口。网页登录是一个页面（扫码 / 短信），确认后由站点自己种
  `sessionid`。逆向 passport 流程要猜设备参数和签名，参考项目也没有实现——它只有一个拿
  `__ac_nonce`/`tt_scid` 的 WebView 工具（`DouyinWebViewCookieAndroid`），真正的登录参考是它给
  B 站做的 `BilibiliWebLoginSheet`。
- 登录态的判据是 `sessionid` / `sessionid_ss` / `sid_tt`；`ttwid` 是每个请求都带的匿名
  cookie，**不能**当成登录。

### 怎么做的

**一、扫码登录（WebView + cookie 捕获）**

- 新增 `DouyinWebLoginSheet`：`Dialog` + `WebView` 加载 `https://www.douyin.com/`，用户在页面
  右上角点「登录」扫码；每 800ms 读 `CookieManager.getCookie("https://www.douyin.com")`，出现
  会话 cookie 就把整条 Cookie 头回传并关闭。WebView 的 UA 与 REST 请求一致（否则抖音会把会话
  当成另一个客户端）。
- 设置页「账号」区新增「抖音账号」卡片：未登录「扫码登录」，已登录「退出登录」，并说明
  房间号搜索不需要登录。
- `UiState.douyinLoggedIn`、`UiAction.DouyinLoggedIn(cookie)` / `LogoutDouyin`；
  ViewModel 只负责落库并回报"是否真的拿到会话"（避免"点完显示已登录、其实没登录"）。

**二、cookie store 从"替换"改成"合并"（这是登录能生效的前提）**

`ttwid` 来自匿名协商、`sessionid` 来自登录，到达时间不同。原来的 `save()` 整体替换，后到的会把
先到的抹掉——症状是"刚登录，搜索还让我登录"。现在 `mergeDouyinCookies()` 合并、同名以后者为
准；`DataStoreDouyinCookies` 与内存实现都走它。另外 `DouyinApi.cookieHeader()` 删掉了进程内
缓存：登录是在运行中写入的，缓存会让后续请求继续发匿名 `ttwid` 直到下次启动。

**三、按昵称搜索**

`DouyinApi.search` 分两条路：

- 纯数字 → 仍走 `room/web/enter`（参考项目的做法，不需要登录）；
- 其它关键词 → 有会话才请求 `aweme/v1/web/live/search/`；没会话时抛
  `PlatformAuthRequiredException`，文案直接指出「设置 → 抖音账号」。

请求参数与解析形状取自 `dart_simple_live` 的 `DouyinSite.searchRooms`：`search_source=switch_tab`、
`count=10`、`webid`、`pc_client_type` 等；响应里 `data[].lives.rawdata` 是**再次编码的 JSON
字符串**，解开后与分区列表同构（`owner.web_rid`、`stats.total_user`、`cover.url_list`…）。
解析是防御式的：形状不对返回空列表，被拒就把平台自己的 `status_msg` 抛给用户。

**四、文案**

搜索框 label 改成「输入抖音房间号或主播昵称」（原来写「搜索 抖音 主播 / 直播间」，而当时只能
收房间号）；空态提示说明"房间号不用登录、昵称要先登录"。

- 上一轮留下的性能项（抖音关注列表刷新每房间 536 KB）仍在待办里。

## 第四十四轮迭代：登录状态纳入同步（B 站 / 抖音）

### 需求

第三件事：把抖音、B 站的登录状态同步过去。用户的取舍说得很清楚——"没连接上同步的机子
肯定不传啊"，也就是只发给已配对设备即可，不要求加密。

### 决定

- **新增 `SyncScope.CREDENTIALS("credentials", "登录状态")`**，这是对第三十二轮"只同步关注
  列表"的反转。反转的理由写进枚举文档：登录是用户不愿在两台设备上重复做的第二件事，而当时
  被删掉的两个范围（搜索历史、播放/弹幕设置）依然不在。
- **不加密**。payload 只可能送到已配对设备（`SyncHttpServer.authenticate` 在读 payload 之前
  就校验配对密钥），解除关联后不再发送。加密方案（HKDF(两端 pairing secret) → AES-GCM）写在
  `CredentialStore` 的注释里，等真要跨不可信网络时再做。
- **不加开关**。用户要的是"同步的时候顺手带过去"，同步页把两个范围如实列出来即可。

### 怎么实现的

- `CredentialStore`（app 模块）在两条 cookie 之上只多存"时钟与墓碑"：每个平台一条
  `SyncRecord`（`login:bilibili` / `login:douyin`），value 是 `{header}`；退出登录写**墓碑**，
  否则对端会在下一次交换里把自己的旧登录发回来。合并仍走 `SyncMerge` 的 HLC + deviceId。
- 两个 cookie 的 DataStore 仍是请求读取凭据的唯一来源；`CredentialStore` 在 `set`/`apply` 时
  把记录镜像进去，所以"同步来的登录"下一次请求就生效。
- 登录/退出全部改走 `credentialStore.set(...)`：抖音扫码成功、B 站二维码确认、两处退出登录
  都带一个新的 HLC。顺带删掉了 `BilibiliAuth.logout()`——它只清本地 cookie，不产生墓碑，
  现在由 `CredentialStore` 负责，留着就是一条会把登录"清回来"的错误入口。
- 同步页「同步内容」列出「关注列表 · 登录状态」，并写明：只在局域网内、只发给已配对设备、
  明文传输、解除关联后不再发送。
- `FollowsOnlySyncTest` → `SyncScopesTest`，断言改成"两个范围"，并新增"登录能出 payload"。
  新增 `CredentialsSyncTest` 4 条（登录落到 cookie store、退出留墓碑、对端登录填本地、
  对端墓碑清本地）。

## 第四十五轮迭代：抖音登录页换成 sso.douyin.com

### 缺陷是什么

用户真机截图：登录弹层里的 WebView 把抖音渲染成"巨大的、横向被裁掉"的一屏——只看到「验证码登录 /
密码登录」几个超大的字和一个被裁掉一半的手机号输入框，二维码根本不在视野里，等于不可用。

### 为什么会这样

两件事叠在一起：

1. 第一版加载的是 `https://www.douyin.com/`，还要求用户自己在页面右上角点「登录」。
2. UA 用的是桌面 QQBrowser（为了和 REST 请求一致），抖音于是按**桌面布局**（约 980 CSS 像素）
   返回页面；而 WebView 默认 `useWideViewPort=false`、`loadWithOverviewMode=false`，980px 的页面
   被塞进 ~410dp 的视口**且不缩放**——结果就是裁切加巨大文字。

### 怎么修的

- **直接打开真正的登录页** `https://sso.douyin.com/`：标题是「登录抖音短视频」，自带
  `width=device-width` 视口，SDK 配置里就有 `/get_qrcode`。二维码就是首屏，不需要找按钮。
- **补上 SSO → 站点的 cookie 交接**：sso 上的会话是 host-scoped 的，而所有 REST 调用读的是
  `www.douyin.com`。新增 `douyinLoginProgress(siteCookie, ssoCookie)` 三态
  （`Waiting` / `Handoff(siteUrl)` / `Done(cookie)`）：一旦 sso 有会话就导航到 www，让站点在
  重定向里种下自己的 cookie，再判定完成。这三步拆成纯函数并有 3 条单测——如果把 sso 的会话
  直接当成"完成"，存下来的头 API 根本用不了；当成"等待"，扫码成功后弹层会一直转。
- **视口兜底**：`useWideViewPort=true`、`loadWithOverviewMode=true`、支持双指缩放，并加一个
  「刷新」按钮。这样即使某个页面没有移动视口（例如回退到 www），也不会再被裁成一屏。
- 文案改成「用抖音 App 扫下方二维码；登录成功会自动返回。页面可双指缩放。」

## 第四十七轮迭代：把抖音登录页的 CSS 视口钉到桌面宽度（找回扫码那一栏）

### 缺陷是什么

第四十六轮之后，弹层里终于能看到抖音的登录框了，但只有「验证码登录 / 密码登录」两个 tab，
**没有二维码**。用户同时给了对照：同一台手机自带的浏览器打开 `www.douyin.com`，登录卡是
**两栏**——左边是二维码，右边才是验证码/密码。

### 为什么会这样

同一个页面、同一个 UA（我们的 WebView 用的是桌面 QQBrowser，浏览器也是桌面 UA），差别在
**CSS 视口宽度**：

- 手机浏览器打开一个没有 viewport meta 的页面时，按约 980px 布局，再缩放到屏宽 → 登录卡走
  "宽档"，两栏，二维码在左；
- 我们的 WebView 虽然开了 `useWideViewPort` / `loadWithOverviewMode`，但 SPA 在渲染过程中
  会自己写 viewport meta，实际布局停在约 411 CSS px → 登录卡走"窄档"，折成一栏，二维码列被
  整个折掉。

`www.douyin.com` 的 SSR 壳里**没有** viewport meta（实测两种 UA 都一样，72 914 字节）——它是
SPA 运行时加的，所以我们无法只在设置里解决。

### 怎么修的

`onPageFinished` 里注入一段 JS，把 `<meta name="viewport">` 钉成 `width=768`，并挂一个
`MutationObserver` 顶住 SPA 的重写；768 是两栏登录卡还能保住的那一侧宽度。视口一变，
CSS media query 重新求值，二维码列就回来；整页仍由 `loadWithOverviewMode` 缩放到屏宽，可以
双指放大。

| 检查项 | 结果 |
| --- | --- |
| `:app:lintDebug` | ✅ |
| JVM 单元测试 | ✅ 582 条，failures=0 errors=0 |
| 仪器测试 | ✅ |
| Release assembly（R8） | ✅ |
| CI | ✅ `68c5082` 三个 job 全绿 |

### 没做到的

- 仍然要真机确认——注入视口属于"只能在设备上看到结果"的改动。若两栏卡片出现但二维码很小，
  下一步是把 `width` 调到 980 或整页放大。
- 若视口改了卡片却仍是单栏，说明抖音是按 JS 的 `window.innerWidth` 一次性决定布局（不是 CSS），
  那就需要在加载前注入（WebView 没有 document-start 注入点），可行方向是改用
  `WebViewAssetLoader` 或者干脆换成手机 UA 让站点给移动版登录页。届时不再靠猜，先在真机上
  用 `chrome://inspect` 看一次 DOM。
- 原生二维码接口（`passport/web/get_qrcode/`）实测被反爬拦（`error_code 4031`），不做。

## 第四十八轮迭代：四个平台各补一个聚合入口（用户报告：没有推荐/全部页）

### 缺陷是什么

用户问："斗鱼虎牙斗鱼B站没有推荐或者全部的页面吗"。查下来是没有，而且不是"少了个按钮"，
是**首页根本不存在"先随便看看"这个动作**。

`MainViewModel.loadCategories` 用 `categories.firstOrNull()` 决定落点，于是：

| 平台 | 冷启动落在 |
| --- | --- |
| 斗鱼 | 英雄联盟（`cate2Info` 的第一条） |
| 虎牙 | 英雄联盟（`huya_categories.json` 的第一条） |
| 哔哩哔哩 | 英雄联盟（`bilibili_categories.json` 的第一条） |
| 抖音 | 和平精英 |

用户必须先在 400+ 个分区里挑一个才能看到任何直播。

### 为什么会这样

不是漏做，是**入口不可达**，三处各有各的原因：

1. **斗鱼**：`mixListV1` 的 level 前缀只有 `2_<cate2Id>` 和 `3_<cate3Id>` 两种，代码里
   `prefix = if (level == 3) "3" else "2"` 把"聚合"这种可能整个排除了。而
   `douyu.com/directory/all` 实际调的是 `0_0`。
2. **虎牙**：`HuyaApi.rooms(gid, ...)` 直接把分类 id 当 `iGid` 发，`iGid=0` 是
   `huya.com/l`「全部直播」的入口，但目录表里没有 0 这一项，所以从来没有被请求过。
   另外 `hasMorePages` 有 `totalPages > 0 && total > 0` 的双重条件，而 `iGid=0` 报
   `iTotal: 0` / `iTotalPage: 73` —— 即使接上，也只出 120 条就"到底"。
3. **哔哩哔哩**：`BilibiliApi.hotRooms`、`BilibiliArea.HOT`、`BilibiliCategories.HOT_ID = "0:0"`
   全都在，`BilibiliPaginationTest` 也在测它。但 `0:0` **不在打包的 456 个分区里**
   （grep 资源文件 0 匹配），UI 永远产生不出这个 id —— 这段代码只有测试在调用，线上从未执行。
4. **抖音**：`DouyinCategories` 整个对象是死代码，注释写着"退化成单个推荐 tab"，但
   `DouyinAdapter.categories()` 走的是 `DouyinCategoryCatalog.load().ifEmpty { api.categories() }`，
   而 `api.categories()` 返回 `emptyList()` —— 那个 `推荐 720` 从未被渲染过。

**抖音保持分区**（用户明确选择）：推荐流只有 6 条，单独做一个 chip 会给"点了推荐只有一屏"

### 怎么修的

聚合项**就是 `Category`**，新增 `isAggregate` 标记与 `Category.ALL_ID = "all"`，因此它走与
真实分区完全相同的选中 / 请求 / 渲染路径，没有第二套分支：

  兜底成 HOT，所以 `rooms` 无需特殊分支；
- `MainViewModel` 落点改成 `firstOrNull { !it.isAggregate }`，只有"目录里除聚合项什么都没有"

## 第四十九轮迭代：默认落在「全部直播」（用户报告）

### 缺陷是什么

上一版装到手机上，首页默认选中「英雄联盟」，用户要的是「全部直播」。

### 为什么会这样

第四十八轮我把落点定成 `firstOrNull { !it.isAggregate }`，注释里写的理由是"聚合项没有分组、
没有三级分类，落在它上面会让分组 chip 和三级行同时为空"。

这是**从"行要显示什么"倒推**出来的判断，不是从"用户打开 app 想干什么"倒推的。聚合项没有
分组正是它的定义，不是缺陷；分组 chip 显示「全部分类」、三级行不出现，本来就是该状态应有的
样子。我把"界面上有两个东西空着"当成了"状态不完整"，于是绕开了一个恰好是正确答案的选项。

用户一句"默认是全部"就否掉了这个推理。

## 第五十轮迭代：关注分组（多分组）与收藏分区

用户要求两件能力：**收藏分区**，以及**关注里能自建分类、把关注的放进去**。方案往返三轮才定稿，
因为三个决定改变了数据模型本身：

| 问题 | 决定 | 后果 |
| --- | --- | --- |
| 一个主播能进多个分组吗 | 能 | 成员关系必须独立成记录 |
| 收藏跨设备同步吗 | 同步 | 进 `FOLLOWS` scope，零额外成本 |
| 「我的分区」放哪 | 平台 tab 正下方 | 按当前平台过滤，空则整行不出现 |
| 能收藏「全部直播」吗 | 不能 | UI 说明 + 存储层拒绝 + 读取侧过滤 |

### 一、为什么成员关系必须独立成记录

这是本轮唯一的架构决定，也是"多分组"这个需求真正的代价所在。

第一版方案打算在房间记录上挂 `groupId`（单值）。改成多分组之后，自然的下一步是
`groups: List<String>`。**这一步是错的**，而且错得很隐蔽：

手机把房间 A 加进「游戏」，平板把同一个 A 加进「音乐」。两条写入落在**同一个 key 的同一个
字段**上，合并时 HLC 一比只剩一个赢家——用户加的两个分组丢了一个。这正是 HLC 存在的理由，
却在字段粒度上被绕过去了。

改成 `member:<groupUuid>:<platform>:<roomId>` 之后，两次添加是两个 key、两条时钟，两边都活。
顺带白拿三个好处：

1. **组内顺序免费**。`member` 记录反正要写，值里塞个 `order` 就有了"在「游戏」里 A 排第一、
   在「全部」里排第五"。第一版方案把这个列为"v1 不做"，现在成本为零。
2. **`updateSnapshot` 的坑结构性消失**。上一版方案里有一条必改项：后台每 30 分钟刷新快照会
   抹掉房间记录上不认识的字段（旧的 `FollowStore.updateSnapshot` 只显式保留 `order`）。成员
   关系不在房间记录上之后，这个缺陷类别不存在了——不是修掉，是不会发生。
3. **删除分组是一次原子写**。分组墓碑 + 它名下所有成员墓碑用同一个 HLC 写下去，对端不可能
   看到"分组没了但成员还指着它"。

### 二、key 词表

记录集从"一个关注列表"变成四种记录共用一份：

```
room:<platform>:<roomId>               房间本身（名字、封面、开播状态、全量顺序）
group:<uuid>                           用户自建分组（名字、顺序）
member:<groupUuid>:<platform>:<roomId> 「这个房间在这个分组里」（组内顺序）
fav:<platform>:<categoryId>            收藏的分区
```

解析规则只有一条：**前缀之后，按第一个冒号切一次，剩下的是"其余全部"**。成立是因为
`platformId` 是四个固定值、`groupUuid` 是 UUID，都不含冒号；而分类 id 含冒号也无所谓——
B 站是 `"1:2"`，抖音是 `"partitionType:partition"`，它们永远是最后那一段。

`LibraryKey.decode` 对未知前缀返回 `null` 而不是猜。旧的裸 key `<platform>:<roomId>` 因此
不会被误读成房间，否则"迁移没跑"会看起来像"跑过了"。

### 三、SCHEMA 1 → 2

key 词表变了，老版本收到新 key 会静默丢弃（解不成房间，`toStreamer` 返回 null）。升到 2
之后，老设备被 `applyPayload` 拒成"对端版本过新"——用户明确说过不考虑兼容，这比静默丢数据好。

`UserSettings.followRecords` → `libraryRecords`，另加 `recordsVersion`。v1 的裸 key 在首次
读取时一次性改写成 `room:` 前缀。**这不是兼容层**：旧 key 是被替换掉的，不会和新 key 并存，
`recordsVersion` 到 2 之后这段代码可以整块删除。保留它的唯一理由是不能因为一次内部重构
把用户 200 条关注清零。

### 四、顺手修掉的既有缺陷

**`MoveFollow` 的索引错配。** `FollowScreen` 交给 `ReorderableFollowList` 的是**过滤 + 直播
优先排序后**的列表，拖动回调给的是那个列表里的索引；而 `moveFollow` 拿它去操作**全量**列表。

复现：关注 3 斗鱼 + 3 B站，点「斗鱼」筛选，把第 1 行拖到第 2 行——写进全量顺序的是全量列表的
index 1，被挪走的可能是另一个平台的人。

修法是把 action 从 `MoveFollow(streamer, index)` 换成 `SetFollowOrder(keys)`，由
`FollowOrdering.moveWithin(full, visible, moved, toIndex)` 以**邻居 key** 为锚点回填全量列表。
视图顺序 → 存储顺序的映射从此只存在于这一个函数里，也才有单测可写。

顺带修掉第二个隐性问题：原来拖动写回的是"直播优先后的顺序"，某人一下播就永久掉到列表尾。
按锚点插回全量之后，存储顺序保持纯手动，**直播优先永远只是视图规则**。

### 五、界面

**首页**：平台 tab 正下方新增「我的分区」行。放在 tab 下面是一个关于范围的声明——tab 下面
的一切都属于那个平台，所以这一行只显示当前平台的收藏。空则整行不出现（这正是上一次
「分区订阅」被删掉的原因：一行永久占位却只重复了"选个分区"）。

**关注页**：原来一个 `LazyRow` 里混着「全部/直播中/未开播/斗鱼/虎牙」两个正交的轴，现在拆成
分组行（主航向）+ 状态·平台行（筛选）。行尾 ⋮ 打开分组多选。

**分组管理面板**画在 activity 窗口内而不是 `ModalBottomSheet`，理由和 `CategoryPicker` 一样：
截图 harness 抓的是 `onRoot()`，dialog 是另一个窗口抓不到，这一页就失去唯一的视觉证据。

缺失时（刚建组、刚加人、state 还没刷新），`scoped` 回退成全部关注——**选了「音乐」却看到
「游戏」里的人，分组筛选静默失效**。

这条是测试写对了才暴露的。修法是分开两个事实：成员关系读 `roomGroups`，`groupRoomOrder`

## 第五十一轮迭代：分类改成内联展开树、卡片分区角标、LibraryStore 拆分

### 一、分类：从弹面板改成内联展开

原实现是一个「选择分类」chip 打开半屏面板，面板里先选分组再选分区。参考图
不是这样——它是**内联展开**。

| 参考图 | 改前 | 改后 |
| --- | --- | --- |
| 一行分组 chip + 右端 ∨ | 一个 chip 打开面板 | 一行分组 chip + 右端 ∨ |
| 点 ∨ 用 FlowRow 铺开全部分组 | 面板里再选分组 | FlowRow 铺开，∨ 变 ∧ |
| 分组行下有分区行 | 面板里选分区 | 分区行直接跟在下面 |
| 两行各有一个「全部」 | 无 | 都有 |
| 选中项带 ✓ | 仅填充色 | ✓ + 填充 |

面板有两个参考图没有的代价：树在打开前不可见；选完分区面板关闭，想比较两个
分区就要反复打开。

**关键语义：浏览分组 ≠ 选中分区。** 点「网游」只改变下面列出哪些分区，不改变
网格显示什么；点「英雄联盟」才换网格，且「网游」保持高亮。参考图就是这个行为
（网游高亮着，英雄联盟被勾选）。

高度代价可控：收起态一行分组 + 一行分区，展开态由**分组数**决定（斗鱼 12 组），
不由分区数决定（400+）。展开后分区行仍在 220dp 以内。

### 二、CI 抓出的真实缺陷：列表不跟随选中的分区

浏览与选中解耦之后，从收藏 chip 选一个别组的分区，分区行仍停在上一个分组，
**被选中的 chip 根本不在行里**，看起来像"选择丢了"。

`categoryLevelsOf` 改成三级回退：用户手选的分组 → 选中分区所属的分组 → 第一个分组。

这个缺陷只有在测试里构造"选中的分区不在当前浏览分组"时才会暴露，手工点两下
发现不了。

### 三、我漏掉、后来补上的一处

第一版漏了**分组行首的「全部」**。参考图两行都有「全部」，而它们含义不同：
分组行的「全部」是"所有分组的分区一起列"，分区行的「全部」是"整个平台"。

实现用哨兵值 `ALL_GROUPS` 而不是 `null`，因为 `null` 已经表示"还没手选过"，
两者必须可区分——前者回退到选中分区所属分组，后者是显式选择、要覆盖回退。

`CategoryLevels` 增加 `browsingAll`：单分组平台同样没有 `activeGroup`，但那里
根本不画分组行，不能靠 `activeGroup == null` 判断「全部」是否选中。

### 四、卡片分区角标

参考图卡片右下角印分区名。`Streamer.categoryName` 从斗鱼和虎牙的解析器写出来

### 五、LibraryStore 拆分

上一轮记录里列为"最该做的重构"。四种记录的规则、一个迁移、一个版本常量和一份

按**变化的理由**拆，不是按行数拆：

| 文件 | 负责 | 变化的理由 |
| --- | --- | --- |
| `LibraryCodec` | 每种记录的 JSON 形状 | 线格式变了 |
| `LibraryRecordSet` | 加载、迁移、写回、缓存、通用写入 | 存储变了 |
| `LibraryStore` | 四种记录的规则 | 产品变了 |

行为一行没改。接缝本来就存在——`records()` 之外的读写都走 `persist()`，编解码
早已集中在一个 `internal object` 里——只是没切。

`RECORDS_VERSION` 跟着 `RecordSet` 走：它描述的是存储词表的版本，不是任何一条
产品规则。

## 第五十二轮迭代：关注页三个筛选全部搬进 UiState

## 第五十三轮迭代：关注页去掉自定义分组，只剩两个筛选（用户要求）

用户的原话是"关注这里还是还原回去吧，不用自定义分类了"。问清范围之后确认了两件事：

| 问题 | 回答 |
| --- | --- |
| 回退到哪一步 | 连首页的「我的分区」收藏一起回退到第五十轮之前 |
| 已经建过分组的设备怎么办 | 记录集版本升到 3，加载时丢掉 `group:` / `member:` / `fav:` |

第五十轮加的是两件互相独立的事——关注分组与收藏分区。它们在同一批提交里，
共用一份记录集和一次 schema 迁移，所以"只删分组、留着收藏"会把那份共用结构留成
半死状态；用户选了整块回退，本轮就按整块做。

### 删掉的是什么

界面：

- `FollowGroupSheet`（分组管理 + 逐房间归档）与 `BulkFileSheet`（多选批量归档）
  整文件删除，连带 `LongPress.longPressOnly`——它唯一的调用点就是分类 chip 的长按收藏。
- `FollowScreen` 回到"状态 + 平台"两行筛选：分组 chip 行、`管理` / `多选` 按钮、
  行尾 `⋮`、行内分组标签、多选态下的选中边框全部消失。
- 首页 `FavoritesRow`（「我的分区」）与分类 chip 上的长按收藏一起删除。
- `UiState` 去掉 `roomGroups` / `followGroups` / `groupRoomOrder` / `selectedFollowGroupId`
  / `favorites`；`UiAction` 去掉十个与之对应的 action。
- `SyncScope.FOLLOWS` 的显示名回到「关注列表」，同步页两段说明文案同步改回。

数据：

- `LibraryStore` / `LibraryRecordSet` / `LibraryCodec` 改名为 `FollowStore` /
  `FollowRecordSet` / `FollowCodec`，`AppContainer.libraryStore` 变回 `followStore`。
  这与第五十轮之前的命名一致，git 历史里两个名字都能对上。
- `LibraryKey` 只剩 `Room` 一种；`Group` / `Member` / `Favorite` 三个类型删除。
- `RECORDS_VERSION` 2 → 3。

### 三个不显然的决定

**一、版本 3 是"丢掉"，不是"写墓碑"。** 这三种记录已经没有读方，留着只是把死重量
推给每个对端。墓碑在同步语义上更干净，但它需要在加载时就有 HLC 和设备号——那时
同步引擎还不存在——而这份分组在本机已经不可见了。所以选丢弃。

代价是诚实地记在这里的：**仍在使用旧版本的已配对设备会把分组再推回来**，新版本
每次都会丢掉它，旧设备那边则一直看得见自己的分组。这是"降级功能不带迁移"的必然
结果，不是遗漏。

**二、`normalize()` 在每次加载和每次 `replaceAll` 都跑，不是一次性迁移。** 一次性
迁移的前提是"旧数据只会出现一次"，但一个仍在旧版本的对端可以随时推进来
`group:` 记录。只在加载时丢，`apply()` 收下的记录会被原样存下并回推给所有对端。

**三、`SCHEMA` 不动。** `room:` 记录的 JSON 形状没变，schema 描述的是**布局**而不是
**种类集合**。升 schema 会让所有已发布设备拒绝与新版配对（`SyncEngine.applyPayload`
对 `payload.schema > SCHEMA` 回"对端版本过新"），而旧对端多出来的那几个 key 只是
被忽略。为了"少收几个会被丢掉的 key"去切断整个配对链路，代价不对等。

### 一个跟着改的细节

`FollowSyncTarget.apply()` 原来拿**收到的**记录数去比 `before` 映射，于是一个旧对端
推进来的 `group:` 记录会被记成"同步了一条数据"——同步日志会声称移动了它根本没存的
东西。现在按 store 里**留下的**记录数，`FollowStoreTest` 里那条
`a retired record kind arriving from a peer is dropped on apply` 钉住了它（断言
`applied == 0`）。

### 顺手记下的两处旧账（本轮未动）

- `UserSettings` 的字段改名为 `followRecords`，但保留了 `@SerialName("libraryRecords")`。
  改线名会让已有安装读出一个空字符串，也就是"一条关注都没有"——内部重构不该清空
  用户的关注列表。
- `HomeScreen` 里有四个从来没用过的 import（`clickable` / `getValue` / `setValue` /
  `pointerInput`），`UiState` 里有一个（`RoomPage`）。这些在本次改动**之前**就在，
  按"改哪个文件就顺手收拾干净"的原则清了 `AssistChip` 与 `StarBorder`（这两个是本轮
  删功能后变成孤儿的），其余四个没动——它们是既有问题，混进一次功能性提交会让 diff
  更难读。

### CI 抓出的问题

一条，是测试自己写错，而且正是本轮改动最该警惕的那类混淆：`FollowStoreTest` 里把
`room:douyu:288016`（记录 key）与 `followed()` 返回的 `Streamer.key`
（裸 `douyu:288016`）当成同一种东西直接断言。CI 的报错
`expected:<[room:douyu:288016]> but was:<[douyu:288016]>` 把两个命名空间摆在一起，
一眼就能看出问题。两条断言现在各读各的映射，注释里写清了区别。

## 第五十四轮迭代：特别关注头像行 + 两列卡片网格（用户要求）

用户给了一张 B 站关注列表的截图，要求"参考这个加上上面的特别关注，下面的一排显示俩个
这样来展示"。问清两件决定改动大小的事之后确定：

| 问题 | 回答 |
| --- | --- |
| 特别关注怎么来 | 新增标记，跟着关注记录同步 |
| 两列网格里还拖不拖 | 头像行可拖，网格不拖 |

### 布局

顶部一排圆形头像（在播绿环 + 名字一行），尾部一个「＋」；下面是两列封面卡片。

这不是"把单列行压成两列"那么轻。旧的行是 56dp 缩略图 + 两行文字，宽度全花在
文字上；参考页把同样的宽度花在封面上，一张卡能直接看出在播什么。所以卡片复用
首页的 `StreamerCard`（16:9 封面 + 标题两行 + 主播行），而不是改造旧行。

### 特别关注怎么存

标记是房间记录上的一个 `special` 字段，不是第二种记录。

第三轮删掉的 `member:` 记录恰好是反例：独立记录意味着"房间"和"标记"两把 HLC，
要处理"标记指向一个已经取关的房间"。挂在房间记录上就只有一把时钟，
**手机加、平板删由 HLC 分出胜负**——对一个布尔值是正确语义，而不是丢数据。
（多分组当初必须独立成记录，是因为那是"多对多"、"两边都可能正确"；这里不是。）

两个容易被忽略的写入点，都补了测试：

- `updateSnapshot`（后台每 30 分钟刷新）会**重新构造**整条记录。漏了标记，
  头像行就会每半小时自己清空一次，而截图看不出来。
- `toggle` 的"重新关注"分支。这里本轮的记录**先写错了一句**，见下面「被测试抓出的
  错误假设」——实际语义是取消关注会把位置和标记一起清掉。

字段**只在为 true 时写入**。永远写 `special: false` 会让每条记录在下次排序时都
被重写一遍，等于给全量记录制造无意义的版本冲突。

### 被测试抓出的错误假设

我在 `toggle` 的注释里写"取消关注后重新关注，位置和特别关注都继承"，并照着写了
测试。第一次跑 CI 就红了：`expected:<[douyu:1]> but was:<[]>`。

根因是墓碑**不带 payload**（`LibraryRecordSet.tombstone` 写的是 `value = null`），
所以重新关注时没有任何东西可继承——那个 `existing?.value?.get("order")` 分支
对一个真正的墓碑永远是 null。更糟的是，仓库里还有一条**从来就不成立**的老测试
`re-following keeps the manual position`：它的名字与注释都在描述"继承"，但它从没
真正走过被打墓碑的那条路径，所以一直是绿的。

改法是把语义说清楚，而不是把代码改成注释的样子：

- 取消关注 = "我不再看这个人"。位置和特别关注标记一起清掉，重新关注时排在末尾、
  不带星。**这才是用户会预期的行为**——一个他从未重新给过的标记不该自己回来。
- 注释与两条测试都按这个语义重写，测试名从 `...keeps the manual position` 改成
  `re-following starts from scratch`，并在注释里记下旧测试为什么一直绿。

这是本轮最有价值的一条：**注释和测试互相印证，但两者都与代码不符时，绿是假的。**

### 拖动排序搬到了头像行

这是本轮唯一有风险的决定。网格里长按拖动要处理两件事：把二维位移解成格子、
和滚动抢手势。头像行是一维，不会有这两个问题，而且它本来就比网格更"该由用户
决定顺序"——网格是浏览面，按在播优先排才有意义。

**头像行不跟随下面的筛选**。筛选是"这一屏看什么"，特别关注是"我常看谁"；
如果按了「直播中」就把离线的那几个常看主播从顶部抹掉，这一行的内容会取决于
它下面的控件，位置也一直在跳。它只与关注列表取交集（取关的人必须消失）。

于是两条轴分开：

| 面 | 顺序来源 |
| --- | --- |
| 头像行 | 用户拖动的顺序（`SetFollowOrder`，同步） |
| 卡片网格 | 在播优先，同组内用存储顺序断平局 |

**踩到的坑**：第一版给头像用了 `clickable` + 一个独立的拖动 detector。两个
detector 都收 down 事件，长按拖动松手时 tap 也照样触发——每排一次序就把房间
打开了。改成一个 `awaitEachGesture` 里先 `awaitLongPressOrCancellation`：等不到
就是普通点击，等到就自己累计位移。这类"两套手势互相看不见"的问题在 Robolectric
里测不出来，只能靠把两种意图放进同一个处理器来根除。

**另一个坑**：头像列的 `Modifier.clip(CircleShape)` 会把下面的名字一起裁成圆。
剪裁只该加在头像那一层，列本身不能有。

### 顺手修掉的

- 网格卡片上的星在这里表示"特别关注"，不是"关注"——卡片都在关注列表里，
  "取消关注"按钮在这个屏幕没有意义。给 `StreamerCard` 加了 `starLabels`

## 第五十五轮迭代：抖音按房间号搜索被误判成关键词（用户报告）

用户报告："抖音没登录的时候的 id 搜索用不了"。追问界面上出现的原文：

> 显示抖音的关键词搜索需要登录，接口返回 2483 请先登录

这句话把范围缩到了一个分支：它**只可能**来自 `search()` 里"输入不是纯数字"的那条路径，
而且它在**任何网络请求之前**就抛出。也就是说，用户拿着房间号，被要求登录。

### 根因：分类方式比用户的输入方式窄

```kotlin
if (trimmed.all(Char::isDigit)) -> enter（房间号，免登录）
else                            -> 关键词（未登录直接抛 2483）
```

`all(Char::isDigit)` 只接受纯 ASCII 数字，于是下面这些全被推进关键词分支：

| 输入 | 为什么 |
| --- | --- |
| `https://live.douyin.com/xxx` | 从抖音/本应用复制来的就是链接 |
| `… 复制打开` 分享文本 | 抖音的分享文案 |
| `１００２…` 全角数字 | 是 Nd（数字），但不是 ASCII，进 query 也要折回去 |
| `1002\u200B683794` | U+200B 是 Cf，`trim()` 不去，`isDigit` 也不认 |
| `房间号：1002…` | 用户自己加的前缀 |

**"没登录的 id 搜索用不了"的真实含义是"看起来像 id 的输入里，只有 100% 纯数字的才走
id 路径"。**

### 顺带做的实测（不是猜）

写了个一次性的探针脚本（未入库）直接打 `room/web/enter`，结论：

- 带**任意** `ttwid`——包括 `DouyinSigner.FALLBACK_COOKIE` 里那个已过期的——都返回 200 +
  完整房间对象；
- **完全不带 cookie** 才返回 `200` + 空 body。

所以 id 路径本身是好的，`cookieHeader()` 的回退也够用；坏的只是"什么算 id"。这条实测也
再次确认了 `enterRoom` 的空 body → `null` → 搜索显示"没有找到"这条链路，将来如果真报
"没有找到"，就是 cookie 没发出去，不是房间不存在。

### 改法

新增 `DouyinApi.roomIdFrom(raw): String?`：

1. 先按 `live|webcast|v.douyin.com/<path>` 取路径段，链接因此永远不会落到关键词分支；
2. 否则把数字提出来（全角用 `digitToInt().digitToChar()` 折回 ASCII）；
3. 剩余字符只允许空白、零宽字符、全角标点，以及 `房间号：` / `room id:` 这类**标签**
   （标签是词，先按正则剥掉，再判断剩下的）。
   带字母的名字——包括 `红眼阿旺2024`——仍返回 `null`，照旧走关键词。

登录提示与搜索页的 placeholder/hint 补上"也可以直接粘贴直播间链接"。

### 测试

`DouyinSearchTest` +5：链接、分享文本、零宽/全角/前缀、昵称不被吞、`roomIdFrom` 的形状
断言。解析逻辑**先在本地用等价的 Python 逐条跑过 12 个用例再落成 Kotlin 断言**——第一次
跑就抓到我自己的一个错（`房间号：` 里的汉字让 leftover 非空），当场改成剥标签。

| JVM 单元测试 | ✅ failures=0 errors=0 |

## 第五十六轮迭代：字母房间号（AYM0707）也能搜到（用户报告）

用户贴了截图，输入框里是 **AYM0707**，下面仍是"关键词搜索需要登录 2483"。

上一轮（第五十五轮）刚修过"按房间号搜索被误判成关键词"，修法是"先按 id 解析，再判断
是不是纯数字"。这一轮暴露出那个修法的前提仍然是错的。

### 根因：`web_rid` 从来不是数字类型

抖音的 `web_rid` 是**字符串**。除数字形态外，创作者可以拿到自定义号，例如 `AYM0707`
——截图里就是这个。上一轮把"是数字"当成"是 id"的充分条件，于是字母号依然掉进关键词
分支，被要求登录。

**实测确认**（tmp 探针，未入库，2026-11-07）：

    web_rid=AYM0707   -> status_code=0，房间「来啦来啦，开搞开搞」/ DNF王大枪，在播
    web_rid=1002683794 -> status_code=0，房间「我的红眼看了不烧心！！」/ 红眼阿旺，未播

两个都能匿名解析，`enter` 完全正常。所以接口没有问题，"什么算 id"这个判断本身错了。

### 改法

- `roomIdFrom` → `webRidFrom`，判定从"全是数字"改成"**一个 ASCII 单词**"
  （字母/数字/`_`/`-`，1..32 字符）。CJK 仍然不算，所以「红眼阿旺」照旧走关键词。
- `-` 和 `_` 从"装饰字符"里移出：它们可能是 id 的一部分，剥掉就把 id 改坏了。
- **顺序改成"先按 id 试，失败再回退"**，这是本轮的语义改动：
  - 未登录 + id 解析不到 → 返回空结果（"没有找到"）；
  - 已登录 + id 解析不到 → 再走一次关键词（`uzi`、`PDD` 这种单字昵称靠它）。
  这样"拿着 id 被要求登录"这条误报从根上不会再有：一个 ASCII 词要么解析成功，要么报
  "没有找到"，不会在未登录时冒出一句"需要登录"。

### 三次踩同一个坑：断言参数顺序

这一轮 CI 红了三次，全在测试里，而且是**同一类错误**：

| 次数 | 错误 | CI 报的 |
| --- | --- | --- |
| 1 | `assertEquals(message, 1, size)` | None of the following candidates is applicable |
| 2 | `runBlocking { }` 作表达式体，返回 `Pair` | Cannot infer type for type parameter 'T' |
| 3 | `assertTrue("message", condition)` | None of the following candidates is applicable |

前两次我改完就推了，第三次才想到该**扫一遍**而不是修一处推一次。用脚本把文件里所有
`assert*(` 的首参是否为字符串字面量扫出来，一次清干净。

教训和第五十五轮记的一样，但更具体：**jupiter4j 的 message 位置不统一** ——
`assertTrue/assertFalse` 是 `(condition, message)`，`assertEquals` 是
`(expected, actual, message)`，而 `assertNull` 只有 `(actual)` 与 `(actual, message)`。
凭"Java 测试库都差不多"的印象写，就会连错三次。**改完一批断言后要整体扫，不要逐个试。**

同类问题在第五十五轮也出现过（同一个文件、`assertEquals`），当时以为是偶发。

## 第五十七轮迭代：enter 不该带 a_bogus（用户报告，第三次「还是搜不到」）

0.17.2 发出去后用户回："最新版还是搜不到"。但截图里的提示变了：

    上一版：抖音的关键词搜索需要登录（2483）
    这一版：没有找到「AYM0707」

提示变了就说明上一轮的分类修复是生效的——AYM0707 已经走了 id 分支。问题在更后面一步：
`enter` 返回了空，于是 `enterRoom` 返回 null，UI 显示"没有找到"。

### 定位：签名把一个能用的接口打坏了

用探针把三种形态并排打了一遍（2026-11-07）：

| 请求 | 结果 |
| --- | --- |
| `enter?web_rid=AYM0707` | 200，504KB，`status_code=0`，房间「来啦来啦，开搞开搞」 |
| `enter?web_rid=AYM0707&a_bogus=<任意值>` | 200，**0 字节** |
| `enter?web_rid=AYM0707&a_bogus=` | 200，504KB，正常 |

**只要带一个服务端验证不了的 `a_bogus`，这个接口就回 200 + 空 body。** 空 body 解析失败 →
null → "没有找到"。签名算得对不对在这里并不重要，重要的是 `enter` 根本不接受这个参数。

再确认"不带签名"是稳的：三个 id 各请求两次，6/6 正常；不存在的 id 返回
`status_code=4001038` 而不是空 body。所以"空 body"与"房间不存在"本来就是两种可区分的
答案，只是代码把前者也读成了后者。

### 为什么之前没发现

同模块里三个端点的签名要求各不相同，而代码把它们写成了同一种：

| 端点 | 是否需要 `a_bogus` | 依据 |
| --- | --- | --- |
| `partition/detail/room/v2` | **必须**有效签名 | 不带签名直接 444（第二十五轮实测） |
| `webcast/feed` | 带签名可用 | 无签名时的行为未被单独测过 |
| `room/web/enter` | **不能**带 | 本轮实测：带了就空 body |

上一轮我修的是"什么算 id"，一路顺着分类往下查，没有回头看这条请求本身。**教训：
"分类对了但还是没结果"时，下一个要查的是请求本身，而不是继续怀疑输入。**

### 改法

- `enterRoom` 改用手写 query，不再过 `DouyinSigner.signQuery`。注释里写清了上面那张表，
  避免以后有人为了"统一"把签名加回去。
- `enterRoom` 显式判 `status_code != 0` 返回 null（`4001038` = 房间不存在），不再依赖
  "JSON 解析失败"这个副作用来表达"没这个房间"。

这一处同时修好了所有走 `enterRoom` 的路径：搜索、房间详情、播放取流、关注列表状态刷新。

## 第五十八轮迭代：过期 ttwid——上一轮的「enter 不该签名」是错的（用户第四次报告）

用户第四次报告同一症状，并给了一条决定性的线索：**"以前这个能查，你改了之后不能查了"**。
按这条线回去看参考项目，才发现在第五十七轮就把结论搞反了。

### 上一轮错在哪

参考项目 `DouyinWebApiAndroid.fetchRoomEnter` **是给 `enter` 签名的**：

```kotlin
val sign = withContext(Dispatchers.Default) { generateABogus(query, DEFAULT_USER_AGENT) }
val url = "https://live.douyin.com/webcast/room/web/enter/?$query&a_bogus=${sign.encodeURLQueryComponent()}"
```

而且两边的 `aBogus` 实现**逐字相同**（`generateRc4BbStr` + `resultEncrypt(..., "s4")`）。
第五十七轮我看到"带一个随便填的 `a_bogus` 会得到空 body"，就断定"这个接口不接受签名"。
**测的是伪造值——真正的生成器一次都没跑过。** 于是把签名删了，请求形态从此与参考项目不同。

### 真正的根因

这次把仓库里真实的 `DouyinABogus.kt` **编译出来跑**（本机 JDK 25 + Kotlin 2.1.20，
临时目录，未入库），拿到真签名后并排测 cookie 状态：

| Cookie | 结果 |
| --- | --- |
| 新协商的 ttwid | 正常，`status_code=0` |
| 出厂 `FALLBACK_COOKIE`（早已过期） | 正常 |
| 格式损坏的 ttwid | **空 body** |
| 完全不带 cookie | **空 body** |
| 真实签名 / 不带签名（cookie 有效时） | 都正常 |

**空 body 只由 cookie 是否被接受决定，与签名无关。** 而 `cookieHeader()` 只在值**缺失**
时才重协商：长期安装的设备一直存着很久以前协商的 ttwid，此后每个请求都带着它，
于是每个房间都返回空 body → `enterRoom` 返回 null → 「没有找到」。

这解释了它为什么只在用户的设备上出现：我的探针每次都重新协商，永远拿不到过期值。

### 改法

- **恢复 `enter` 签名**，与参考项目一致。
- `enterRoom` 在 body 为空时**丢弃 cookie、重新协商、重试一次**。
  不循环：空 body 与"房间不存在"是可区分的（后者返回 `status_code=4001038`），
  一次重试足够，再空就是真没有。
- 抽出 `renegotiateCookie()` / `negotiateAndStore()`，把"取 cookie"和"换 cookie"分开。

### 这一轮我在方法上的错

前三次修同一个 bug，我都只测**能想到的变量**（判定逻辑、请求参数），而没有测
**参考项目到底怎么发请求**。用户一句"以前能查"就指向了答案——这个线索一直在，
但我直到第四次才用上。**当自己反复修不好时，先对照那份"以前能用"的实现，逐字比对请求。**

另外值得记的：第五十七轮我不仅改错了代码，还**把错误行为写成了断言**
（`enter must stay unsigned`）。这条断言在恢复签名后立刻把 CI 打红——它是这轮唯一
一次"测试正确地阻止了旧错误继续存在"。教训是：**给一个反直觉结论写断言之前，
先确认结论本身来自可复现的实验，而不是一次手搓的输入。**
